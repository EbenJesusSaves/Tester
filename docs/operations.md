# Deploying and operating the OTA service

This profile runs the checked-out xprem server with PostgreSQL, Redis and local asset storage. It provisions multiple apps, each with `dev`, `uat` and `prod` channels. These are release destinations within one deployment. The supplied Compose profile binds only to localhost and is intended for development and acceptance testing; production requirements are listed below.

## Decisions and their reasons

| Decision | Reason and operational consequence |
| --- | --- |
| PostgreSQL control plane | xprem's stateless environment configuration supports one app. Database mode provides multiple apps, channel mappings and transactional release metadata. |
| Independent app IDs and signing keys | Identically named channels and runtime versions remain scoped to their app. Each mobile binary trusts its app certificate. |
| `dev`, `uat`, `prod` channel → same-named branch initially | Each environment gets a predictable publishing destination. Later mapping changes can promote a tested release branch without changing installed binaries. |
| Bootstrap preserves existing mappings | Re-running setup must not roll production back or reset an active rollout. Removed apps are never silently recreated with a new ID. |
| Mounted secrets | Passwords and encryption keys stay out of Git, image layers, Compose environment metadata and command arguments. The wrapper reads them into the server process environment at startup. |
| PostgreSQL signing-key encryption | App signing keys are generated by xprem and sealed using the separate 32-byte master key. Losing that key prevents restoring signing capability from the database alone. |
| Redis shared cache | Multiple replicas need shared invalidation, locks and authentication throttling. A local process cache is insufficient for that deployment model. |
| Redis `noeviction` | Avoid evicting security counters and locks to make room for cached payloads. Alert on memory pressure; failed writes affect service availability. |
| Local persistent asset volume | Gives a runnable setup without a cloud account. Production uses shared object storage and CDN delivery before horizontal scaling. |
| Explicit app ID, no branch surfing | Prevent accidental fallback into another app and keep a channel's configured release selection deterministic. |
| Device/server telemetry disabled | Collect no optional device registry or vendor telemetry by default. Enable collection only after selecting a retention and privacy policy. |
| Non-root, read-only OTA container | Limits writable paths to assets and temporary files. The original compiled binary is reused; the wrapper only loads secrets. |
| Pinned PostgreSQL/Redis image digests | Repeated deployments resolve the same dependency images. Update digests through reviewed upgrades and vulnerability scans. |

**Channels are routing, not access control.** Mobile manifest and asset endpoints are public. A client can claim another channel or app ID; pinned per-app signing certificates protect update integrity, not confidentiality. Never place secrets in OTA bundles. In the community edition, app publishing tokens can publish to every branch of that app; naming tokens `dev` or `prod` does not constrain them. Fine-grained RBAC and API-key branch restrictions are enterprise features. Use protected CI environments and approvals for trusted teams, and separate servers, credentials and signing trust when strict environment/organization isolation is required. Do not rely on a reverse-proxy path rule alone to restrict publishing: upload completion and signed upload URLs are part of the write flow.

## Local setup

Requirements: Docker with Compose v2, Python 3, and network access for the repository's locked Go/npm dependencies. Run commands from the repository root. PostgreSQL and Redis expose no host ports. The app exposes `127.0.0.1:3000`.

1. Generate local secrets and configure the bootstrap admin:

   ```sh
   python3 scripts/ota-init.py --admin-email ota-admin@example.test
   ```

   This creates ignored `deploy/ota/.env` and `.secrets/`. Running it again preserves existing values. The bootstrap admin password is in `.secrets/admin_password`; read it privately for dashboard login. The script uses generated passwords rather than shared example credentials. The secret directory is mode `0700`; files are `0444` so non-root containers can read Compose bind-mounted secrets. Container secret files can be read by processes within the authorized container. This is a local convenience, not a replacement for a production secret manager. Do not run commands that print all container environment variables.

2. Build the server using the existing repository Dockerfile, then the secret-loading layer:

   ```sh
   docker build --build-arg VERSION=ota-local -t xprem-ota-base:local .
   docker compose --env-file deploy/ota/.env -f deploy/ota/compose.yaml build ota
   docker compose --env-file deploy/ota/.env -f deploy/ota/compose.yaml up -d --wait
   ```

   The version stamps serialized cache keys. Production builds must use an immutable release/commit identifier and promote the same image digest through testing and production. The upstream base Dockerfile has moving build tags; pin its build/runtime images in your release pipeline and retain the resulting digest and SBOM. The wrapper accepts `OTA_BASE_IMAGE` for an approved base image. `up --wait` waits for `/ready`; `/hc` answers while startup migration is still in progress, so it is a liveness probe only. After initialization, `/ready` indicates that the router was installed, not an ongoing database/Redis dependency check.

3. Edit a copy of `deploy/ota/apps.example.json` to name your applications, then provision them:

   ```sh
   python3 scripts/ota-bootstrap.py --admin-email ota-admin@example.test
   python3 scripts/ota-smoke.py
   ```

   Use `--apps /path/to/apps.json` for your list. Bootstrap authenticates through the existing dashboard API, creates missing apps/branches/channels and downloads each public certificate. It records generated IDs in `deploy/ota/state/apps.json`. Copy each app's ID and corresponding `*-certificate.pem` into its mobile configuration. The public certificates are safe to commit in the mobile repository; the master key and admin/publishing credentials are not. Use a different `--state` directory for each server. The smoke test checks both platforms for all three channels, health, anonymous management rejection and explicit tenant selection. A runtime with no publication receives a valid no-update response; that does not prove a published update downloads correctly.

The setup script uses a local lock and saves each new app ID immediately. If interrupted after app creation but before saving, it can recover an app by an unambiguous display name. Concurrent provisioning from different machines is unsupported because the create-app API has no idempotency key. Provision from one controlled job. A changed certificate or missing saved app ID is a hard stop requiring operator review.

For a physical phone, use a reachable HTTPS staging origin and configure `OTA_BASE_URL` accordingly; `localhost` on the phone means the phone. Place a TLS reverse proxy on this host in front of the loopback binding, or replace the profile with your production ingress. Do not expose this development profile directly to the Internet. Custom ports require both `OTA_PORT` and `OTA_BASE_URL` to agree, and `--url` on bootstrap must match. TLS certificate validation stays enabled in bootstrap, which refuses remote plain HTTP and credential-bearing redirects.

## Publish, verify, promote and recover

Use the repository's `eoas` CLI or pin a tested CLI version in the mobile project's lockfile. In database mode it uses an xprem-issued `EOO_TOKEN`; Expo account tokens do not authorize the local control plane. Generate an app publishing token in the dashboard and store it in that app's protected CI secret store. Keep it out of mobile binaries and build logs. The CLI reads `expo-app-id` from Expo configuration. Set the mobile example's `OTA_APP_ID`, `OTA_CHANNEL`, `OTA_MANIFEST_URL`, `OTA_RUNTIME_VERSION` and `OTA_CERTIFICATE_PATH` for the intended app and environment; see the mobile client guide for the exact build configuration.

```sh
# In the mobile project, after its lockfile dependencies are installed.
# EOO_TOKEN is injected by the CI secret store, never passed on the command line.
OTA_CHANNEL=dev npx --no-install eoas publish --branch dev --nonInteractive
```

`--branch` selects the publish destination. `OTA_CHANNEL` selects the supplied mobile example configuration; it is not a server-side access restriction. Use an exact runtime compatibility value shared with the installed binary. A native dependency/configuration change requires a new store binary and runtime, followed by an OTA built for that runtime.

Before promoting, verify signature validation and actual bundle/asset downloads on Android and iOS release builds. Exercise first install, embedded fallback, no update, update available, offline/retry, invalid signature and incompatible runtime. Check the published app ID, platform, runtime, source commit and asset hashes. CI should retain the export artifact and release metadata.

For a tested candidate, create a dedicated release branch in the app, publish to it, and map `dev`, then `uat`, then `prod` to it using the dashboard. This serves the same stored artifact and avoids rebuilding different binaries while calling them the same release. The bootstrap leaves these promoted mappings intact. Have a second reviewer approve the production mapping in the CI/change workflow. Community mode does not provide an immutable audit trail; retain signed CI/deployment logs externally.

Use the built-in channel rollout to direct an initial cohort to the candidate branch while the rest remain on the control branch. Increase only after agreed crash/startup/error thresholds pass; reliable cohort assignment requires the client installation ID. Preserve the previous branch and bundles. To stop a bad rollout, choose its **revert** outcome in the dashboard. For an already promoted release, remap the channel to the preserved good branch or republish the known-good update using the supported rollback/republish operation. Keep runtime and platform compatibility. Devices must make another update check to receive the recovery; disconnected devices cannot be remotely forced to reload.

## Production changes

| Area | Required configuration and reason |
| --- | --- |
| Public edge | HTTPS with a valid public certificate; request/header/body limits, upload timeouts, rate limits and DDoS controls. Forward only intended public routes. |
| Admin plane | Restrict `/auth`, `/api`, `/dashboard`, `/mcp` and OAuth endpoints to your operations network/identity gateway. Do not expose `/metrics`; allow only a private scraper if `PROMETHEUS_ENABLED=true`. |
| Request identity | The proxy must overwrite untrusted forwarding headers and the server must trust only your proxy ranges/configuration. Rate limits must not share a spoofable source identity. Consult the checked-out server's proxy support before setting headers. |
| TLS to dependencies | Use managed PostgreSQL with verified TLS (`sslmode=verify-full`) and Redis TLS (`REDIS_USE_TLS=true`, optional `REDIS_CA_CERT_B64`). This local wrapper builds a plain internal DSN; replace it with a secret-manager-injected production `DB_URL`. |
| Secrets | Inject `JWT_SECRET`, master key, DB/Redis credentials via your orchestrator. Do not reuse local generated secrets in production. Mount only the secrets each service needs. |
| Storage | Set `STORAGE_MODE=s3`, `gcs` or `azure` and the corresponding repository-supported provider settings; use workload identity where supported, private buckets, least privilege and versioning/backups. Azure's current adapter requires a shared account key. |
| CDN | Serve immutable, app-scoped assets through a configured supported CDN. Preserve object paths and required compression/hash semantics. Keep manifest responses private and non-cacheable; never cache selection solely by URL. |
| Replicas | Shared PostgreSQL, Redis, secret values and object storage; a unique `CACHE_KEY_PREFIX` per deployment. Local volume assets must not be independently attached to multiple replicas. |
| Capacity | Budget DB connections as replica count × `DB_MAX_CONNS`, plus jobs and administrative headroom. Measure DB/cache latency and object-store/CDN egress before increasing replicas. |
| Observability | Collect edge status/latency, container memory/CPU, DB pool usage, Redis memory/errors and storage errors. Optional user telemetry is disabled here; select an approved client crash-reporting mechanism before release rollout. |
| Probes and termination | Liveness `/hc`, startup/readiness `/ready`, plus independent dependency and end-to-end manifest probes. Allow in-flight upload/request draining during termination. |

Use `CDN_BASE_URL` only with an origin that contains the exact configured app-scoped object paths; CloudFront and direct storage modes have their own signing configuration in `internal/cdn`. The generic CDN does not itself add authorization to a public URL. Keep `ENABLE_PREVENT_CDN_REDIRECTION_HEADER=false` so arbitrary clients cannot force asset traffic through the Go server. Bundle diffing is deliberately off until measured: enabled patch jobs can consume about six times the configured maximum bundle size per concurrent job. Redirect patches to a CDN only when its responses add the protocol's required patch headers.

## Performance validation

No capacity claim follows from successful startup. Establish a baseline against a real published runtime with signing enabled, representative assets and both platforms. The included k6 workload fails if it gets a no-update response instead of a signed manifest. Initial acceptance targets are p95 < 100 ms, p99 < 250 ms and errors < 0.1%; these are proposed service objectives, not measured results.

```sh
OTA_URL=https://ota-staging.example.com \
OTA_APP_ID=the-generated-app-id OTA_RUNTIME=the-published-runtime \
OTA_CHANNEL=uat OTA_PLATFORM=android OTA_VUS=50 OTA_DURATION=5m \
k6 run scripts/ota-benchmark.js
```

Run from a dedicated load generator with k6 installed at an approved pinned version. The one-second think time models periodic checks under concurrency; do not interpret VUs as requests per second. Record actual request rate and load-generator CPU. Repeat warm/cold cache, iOS/Android, different app IDs/channels, candidate/control cohorts, no-update checks and simultaneous publishing. Measure asset transfer separately at the CDN with actual bundle sizes, reporting bytes/sec and error rate. Use a controlled staging cache restart to exercise cold cache; never flush a shared production Redis. Test Redis and DB failure recovery and verify ingress rate limiting still protects authentication: the upstream cache-backed authentication limiter fails open when cache operations fail. Archive k6 results with server image digest, machine/replica sizes, DB configuration, network location and dataset size.

## Backups, upgrades and incidents

Back up PostgreSQL and the matching asset store; retain the master signing-key encryption key in a separate restricted recovery system. Exercise restores into an isolated deployment and compare app IDs, channel mappings, certificate fingerprints and manifest signatures before resuming traffic. A DB restore without the original master key cannot decrypt the app signing keys. Do not simply replace `DB_KEYS_MASTER_KEY_B64`; changing it requires re-encrypting existing key rows through a reviewed migration. A new signing certificate also requires planning client trust distribution through a store binary.

Take a recoverable snapshot before upgrades. Test migrations against a restored database, then promote the exact tested image. `up` may run schema/storage migrations; downgrading the binary does not undo them. Drain replicas, observe startup/readiness, run smoke checks, then perform a signed-manifest plus asset download check for each app. Keep the former image and the recovery snapshot until acceptance completes.

For a leaked publishing token, revoke it in the affected app and issue a replacement into CI, then review all recent publishes/mappings and recover the last known-good release. Changing JWT secrets invalidates signed credentials and affects uploads/sessions; coordinate it across all replicas and reissue credentials. For a signing-key compromise, disabling the publisher alone cannot restore trust: isolate the service, restore/rotate signing trust with a mobile binary rollout, and follow the organization's incident process.

Stop local services with `docker compose --env-file deploy/ota/.env -f deploy/ota/compose.yaml down`. This retains the named database/asset volumes and `.secrets`; deleting them is an explicit data-loss operation. Never run `down -v` as routine cleanup. Bootstrap admin environment values only seed the first account; changing the password file after initialization does not change the existing database account password. Rotate that password through the account API/dashboard and update the local bootstrap password file if further bootstrap runs are required.
